2. Executive Summary 
The Datalake 3.0 application serves field personnel operating in remote, zero-connectivity 
environments. Authenticating these personnel securely, without reliance on network infrastructure, 
is a critical unresolved gap. This Product Requirements Document defines the full specification for 
an offline-first, AI-powered facial recognition and liveness detection module to be embedded within 
the existing React Native application. 
 
The solution must achieve greater than 95% facial recognition accuracy, complete end-to-end 
verification in under one second, remain within a 20 MB model footprint, and operate exclusively 
using open-source technologies. The module must also support deferred synchronisation with an 
AWS backend when connectivity is restored, with automatic local data purging post-sync. 
 
3. Goals & Success Metrics 
3.1  Primary Goals 
• 
Authenticate field personnel reliably in zero-network conditions using on-device facial 
recognition. 
•

5. Functional Requirements 
5.1  Facial Recognition Engine 
1. The system shall enroll a user's facial embedding on-device during initial setup, storing it in 
encrypted local storage. 
2. Recognition shall use a MobileNetV2 or MobileFaceNet backbone, quantized to INT8, 
enabling inference under 350 ms on the target hardware class. 
3. The embedding vector shall be 128-dimensional, compared against stored embeddings 
using cosine similarity with a configurable threshold (default: 0.75). 
4. The model shall be trained on a dataset inclusive of diverse Indian skin tones, face 
structures, and age demographics, validated across subgroups. 
5. The system shall handle at least 500 enrolled facial profiles per device without degrading 
performance. 
6. Re-enrollment shall be possible only through an authorised admin workflow. 
 
5.2  Liveness Detection (Anti-Spoofing) 
7. The system shall perform active liveness checks requiring at least one of the following 
gestures: blink, smile, or slight head turn. 
8. A passive liveness check (texture/depth analysis using a Binary Cross-Entropy model on a 
single RGB frame) shall run in parallel to detect printed photographs and screen replays. 
9. The liveness module shall process and respond within 400 ms. 
10. The combined liveness pipeline (active + passive) shall complete before granting 
authentication approval. 
11. Anti-spoofing shall function under outdoor lighting variations including direct sunlight, 
shadows, and low-light conditions. 
 
5.3  Offline Operation 
12. All recognition and liveness inference shall execute entirely on-device, with zero network 
calls during the authentication flow. 
13. Authentication events shall be logged locally with a timestamp, user ID, verification 
outcome, liveness result, and GPS coordinates where available. 
14. Local session logs shall be stored in encrypted SQLite or Realm database within the app 
sandbox. 
15. The app shall function across unlimited offline sessions until storage is saturated. 
 
5.4  Sync & Purge Mechanism 
16. Upon detection of network connectivity, the app shall automatically queue pending 
authentication records for upload to the configured AWS endpoint. 
17. Sync shall use exponential back-off retry logic (max 5 retries, delays: 2s, 4s, 8s, 16s, 32s) to 
handle intermittent connectivity.

local records shall be purged. 
19. A manual sync option shall also be accessible from the app settings screen. 
20. Sync events shall themselves be logged (sync timestamp, record count, success/failure

5.5  React Native Integration 
21. The facial recognition and liveness module shall be exposed as a single React Native Native

23. The module shall be compatible with React Native 0.71 and above. 
24. Camera access shall be managed through react-native-vision-camera or the standard 
CameraRoll API, with appropriate runtime permission prompts. 
25. The module shall support both debug and release build configurations. 
 
6. Non-Functional Requirements 
6.1  Performance 
• 
Total end-to-end latency (face detection → recognition → liveness result): < 1 second. 
• 
Model cold-load time on first app launch: < 3 seconds on mid-range device. 
• 
Memory footprint of inference engine at runtime: < 150 MB RAM. 
• 
Battery impact: no persistent background processing; inference triggered only on user 
action. 
 
6.2  Model Size & Compression 
• 
Base model file size: ≤ 20 MB (target ≤ 12 MB). 
• 
Quantization technique: Post-Training Quantization (PTQ) to INT8 using TensorFlow Lite or 
ONNX Runtime Mobile. 
• 
Optional: Knowledge Distillation from a larger teacher model (e.g., ArcFace ResNet-50) to 
the student MobileFaceNet. 
• 
Pruning: Structured filter pruning at ≥ 30% without accuracy drop below threshold. 
 
6.3  Security & Privacy 
• 
Facial embeddings shall never be stored as raw images; only the 128-d embedding vector 
shall be persisted. 
• 
All local data (embeddings, session logs) shall be encrypted using AES-256 at rest. 
• 
Sync transport to AWS shall use TLS 1.2 or higher. 
• 
The solution shall comply with India's IT Act 2000 and applicable data localisation 
guidelines. 
• 
No biometric data shall be transmitted to any third-party endpoint.

7.3  Data Flow 
26. User opens authentication screen; camera feed initialised. 
27. MediaPipe detects face bounding box; image cropped and normalised to 112×112 px. 
28. Active liveness prompt displayed (e.g., 'Please blink'); landmark delta computed over 30-
frame buffer. 
29. Passive anti-spoof CNN run on single frame in parallel. 
30. On liveness pass: MobileFaceNet generates 128-d embedding. 
31. Cosine similarity computed against stored embedding for matched user ID. 
32. If similarity ≥ threshold: authentication granted; event logged locally. 
33. On network restore: background sync service uploads pending logs, receives server ACK, 
purges local records.

8.3  Compression Strategy 
• 
Stage 1 — Post-Training Quantization (PTQ): Convert FP32 weights to INT8 using 
representative calibration dataset. Expected 4× size reduction with < 1% accuracy drop. 
• 
Stage 2 — Structured Pruning: Remove filters with L1-norm below threshold (30% sparsity 
target). Re-fine-tune for 5 epochs after pruning. 
• 
Stage 3 — Knowledge Distillation (optional): Train MobileFaceNet student against ArcFace 
ResNet-50 teacher. Soft-label KL divergence loss. Improves accuracy-to-size ratio. 
• 
Stage 4 — TFLite Flatbuffer serialization: Final model stored as .tflite for Android; ONNX → 
Core ML conversion pipeline for iOS.
